# Database access and migration tooling for TypeScript and Postgres

Date: 2026-11-26. Resolves issue #76, part of map #71 (rewrite The Logbook in TypeScript).

Method: claims were read from primary sources (each tool's official docs, GitHub release pages, the npm registry for versions and dates, PostgreSQL's own docs and wiki) during this session. The fetch tool summarises pages, so quotes are as returned by it. Anything a page did not say is listed under "Unverified". Versions are "latest on npm as of 2026-11-26". This note gathers facts and trade-offs; it does not make the decision (that is a separate ticket).

## Summary

Five realistic options: **Drizzle** (schema written as TypeScript, SQL-shaped queries), **Prisma** (schema written in its own language, generated client), **Kysely** (typed query builder only, no schema ownership), **TypeORM** (classic decorator-based ORM), and **plain SQL with a migrator** (e.g. dbmate, node-pg-migrate). They differ on three axes: where the "source of truth" for the schema lives (your code, a Prisma file, or SQL files), how much SQL is hidden from you, and how migrations are produced (generated by diffing, or hand-written).

For this project the facts that matter most: the database already holds data and was built by Django, so the new app must either *adopt* the existing tables (introspect, then baseline) or *build a new schema and copy data in* (the map lists this as a separate ticket). Prisma and Drizzle both document a "baseline" step that marks the existing schema as already applied; Kysely and plain SQL tools simply start a fresh migration history. The Logbook schema uses a case-insensitive unique index (`lower(name)` on `Gym`) and multi-table inheritance (`IndoorRoute` extends `Route`); expression indexes are explicitly on Prisma's list of things `db pull` cannot represent, and Drizzle documents expression indexes (but not confirmed for unique ones). Maturity differs: Drizzle is still pre-1.0 on npm (1.0 is at release-candidate stage), Prisma 7 is current with 8.0 in release candidates, Kysely is pre-1.0 (0.29), TypeORM reached 1.0 in May 2026.

## 1. Concepts, in plain English

### What a database driver is
The library that actually talks to Postgres over the network (for Node: `pg` or `postgres`). It sends SQL text and returns rows. It knows nothing about your TypeScript types. Everything below sits on top of one.

### What an ORM is
An **Object-Relational Mapper** lets you work with database rows as program objects and write queries in the host language instead of SQL strings. Django's own ORM is the one you use today. The word covers a spectrum:

- **Raw SQL + driver**: you write SQL strings. Full control, no safety net: a typo in a column name is found at runtime.
- **Query builder** (Kysely): you build SQL through a chainable TypeScript API, and the compiler checks table and column names. You still think in SQL (joins, group by); there is no hidden behaviour.
- **Full ORM** (Prisma, TypeORM, Drizzle's relational API): you describe models and relationships; the tool decides how to fetch, e.g. "give me this Ascent with its Route and Gym" becomes one or more queries for you.

**The trade: convenience vs control.** An ORM saves typing and gives uniform, checked code for the 90% of simple reads and writes. The cost is a layer between you and the SQL: you must learn its vocabulary, occasionally it generates inefficient queries, and the unusual 10% (window functions, `lower()` indexes, `FILTER` aggregates for weekly summaries or grade pyramids) needs an **escape hatch**: a documented way to drop to raw SQL. How good the escape hatch is, and whether raw results are still typed, is a main thing to compare.

### What type safety means here
Whether the TypeScript compiler knows that `ascent.result` is one of `onsight | flash | redpoint ...` and that a query returns `{ name: string; grade: string }[]`. Two ways to get there: **types derived from a schema you write in code** (Drizzle, TypeORM entities), or **types generated from a schema file or from the live database** (Prisma, Kysely via codegen). TypeScript types vanish at runtime, so none of this validates data coming out of the database unless the driver does. Kysely's docs say as much: "Kysely only deals with types in the TypeScript level" (https://kysely.dev/docs/getting-started).

### What a migration is
A **migration** is a versioned, ordered change to the database *structure* (add a column, create a table, add an index), stored as a file in the repo. The tool records which ones have already run in a bookkeeping table inside the database, so running "migrate" on any copy of the database applies exactly the missing ones. TypeORM's docs: "just a single file with SQL queries to update a database schema" (https://typeorm.io/docs/migrations/why). Django does the same today (`logbook/migrations/0001..0005`, tracked in `django_migrations`). Migrations may also move data (e.g. split one column into two). In Postgres, schema changes can run inside a transaction and roll back as a unit: "one of the more advanced features of PostgreSQL is its ability to perform transactional DDL" (https://wiki.postgresql.org/wiki/Transactional_DDL_in_PostgreSQL:_A_Competitive_Analysis). One exception worth knowing: `CREATE INDEX CONCURRENTLY` (builds an index without blocking writes) cannot run inside a transaction block (https://www.postgresql.org/docs/current/sql-createindex.html), so tools that wrap everything in a transaction need an opt-out for it.

### Schema-as-code vs schema-first (two senses)
- **Where the source of truth lives.** *Code-first*: you edit a schema definition in the application (TypeScript or Prisma's file) and the tool works out the SQL. *Database-first*: the database is the truth, you write SQL migrations by hand and the tool reads the result back into types ("introspection"). Drizzle's docs use exactly this split: `pull` is "database first", `push` and `generate`+`migrate` are "codebase first" (https://orm.drizzle.team/docs/migrations).
- **Generated vs hand-written migrations.** Code-first tools *diff* your schema definition against the previous state and emit SQL. Convenient, but the diff is a guess (a renamed column can look like drop + add, which destroys data; this is general practice, not a claim from the docs read), so generated SQL must be reviewed. Hand-written migrations are more work and fully predictable.

### Push vs migrate
Drizzle's `push` applies the diff straight to a database with no migration file ("the best approach for rapid prototyping"); fine for a throwaway dev database, wrong for one holding real data. Migration files are what you commit and run in production (https://orm.drizzle.team/docs/migrations). TypeORM's equivalent hazard is `synchronize: true`, which its docs caution against once the database holds data.

### Baselining
Adopting a tool on a database that already exists and has data. You create an "initial" migration that describes today's structure and mark it as *already applied* without running it, so the tool only runs later changes. Both Prisma and Drizzle document this (below).

## 2. The options

### 2.1 Drizzle ORM (+ drizzle-kit)
Versions: `drizzle-orm` 0.45.4 (2026-10-08) and `drizzle-kit` 0.31.11 (2026-09-21) are the npm "latest"; v1.0.0 exists only as release candidates (rc.6 on 20 Nov per the GitHub releases page; `1.0.0-beta.*` tags on npm). Pre-1.0 means breaking changes are expected; the rc.6 notes call it "a large breaking release" (https://github.com/drizzle-team/drizzle-orm/releases). License Apache-2.0.

- **Philosophy**: "a headless TypeScript ORM with a head"; "If you know SQL, you know Drizzle"; zero dependencies. Offers both a SQL-like query API and a relational API for nested fetches that "always outputs exactly 1 SQL query" (https://orm.drizzle.team/docs/overview).
- **Schema**: written in TypeScript (`pgTable(...)`). Types are inferred from it directly; no code-generation step for the client.
- **Migrations**: `drizzle-kit generate` diffs the TypeScript schema and writes SQL migration files; `drizzle-kit migrate` applies unapplied ones and logs them in `__drizzle_migrations` (schema `drizzle`, configurable). `push` and `export` also exist. You can run migrations at app start via `migrate(db)` in code, or only generate files and apply them with an external tool (Bytebase, Liquibase, Atlas) (https://orm.drizzle.team/docs/migrations, https://orm.drizzle.team/docs/drizzle-kit-migrate).
- **Custom SQL**: `drizzle-kit generate --custom --name=...` creates an empty SQL migration for hand-written DDL "that Drizzle Kit doesn't support yet, or for seeding data". Custom JS/TS migration scripts were "coming in a future release" per that page (https://orm.drizzle.team/docs/kit-custom-migrations), so data migrations are SQL-only.
- **Escape hatch**: the `sql` template. Usable for a whole statement (`db.execute`) or as a fragment inside a typed query (`where`, `orderBy`, `groupBy`, `having`, selected columns). Interpolated values become `$1` placeholders (injection-safe); `sql.raw()` bypasses escaping and must only get trusted strings. The `sql<T>` generic is "purely a helper": it declares the type but does not convert runtime values (https://orm.drizzle.team/docs/sql). Check constraints and expression indexes can be declared with it; the docs example `sql\`lower(...)\`` is for a regular index, and a *unique* expression index is not shown, so a case-insensitive unique `Gym.name` needs a test or a custom SQL migration (https://orm.drizzle.team/docs/indexes-constraints).
- **Existing database**: `drizzle-kit pull` introspects the live database and writes a `schema.ts`; `tablesFilter` / `schemaFilter` limit scope (useful to skip Django's `django_*` and `auth_*` tables). `--init` marks the pulled schema as an applied migration, which is the baseline (https://orm.drizzle.team/docs/drizzle-kit-pull). The page lists no limitations of the pulled output.
- **Trade-offs**: lightest and closest to SQL, so the least to unlearn; but pre-1.0, the migration tooling is the younger half, and data migrations are SQL-only.

### 2.2 Prisma ORM
Versions: `@prisma/client` 7.10.1 is the stable "latest" (Oct 2026); 8.0.0 is at release-candidate stage (GitHub releases page; npm shows `prisma` 8.0.0-rc.*). Prisma 7 (announced 2025-11-19) rewrote the client from Rust to TypeScript ("rust-free and ESM"), generates client code into your project rather than `node_modules`, and moves settings to a `prisma.config.ts` file; the post claims a 90% smaller bundle and 3x faster queries (https://www.prisma.io/blog/announcing-prisma-orm-7-0-0; vendor's own claims). On Postgres you pass a driver adapter (`@prisma/adapter-pg`) (https://www.prisma.io/docs/orm/overview/databases/postgresql). The 8.0 release candidates list breaking changes, e.g. `pg` becomes a peer dependency you install yourself.

- **Schema**: written in Prisma's own schema language (`schema.prisma`), not TypeScript. `prisma generate` produces the typed client; you re-run it after schema changes.
- **Migrations**: `prisma migrate dev` diffs the schema and writes a SQL migration. It uses a **shadow database** (a temporary scratch database it creates and deletes) to replay your history and detect drift and potential data loss; `migrate deploy` (production) does not use one (https://www.prisma.io/docs/orm/prisma-migrate/understanding-prisma-migrate/shadow-database). Generated migrations can be edited, and `migrate dev --create-only` makes a draft to add hand-written SQL to.
- **Escape hatch**: `$queryRaw`/`$executeRaw` (not covered by the pages read; see Unverified), `$queryRawUnsafe` for dynamically built SQL, and **TypedSQL** (preview feature): you write `.sql` files, `prisma generate --sql` produces typed functions, run via `$queryRawTyped`. It needs a live database connection at generate time, works on Postgres and MySQL, and "does not natively support constructing SQL queries with dynamically added columns" (https://www.prisma.io/docs/orm/prisma-client/using-raw-sql/typedsql).
- **Existing database**: `prisma db pull` introspects into `schema.prisma`. It cannot express every Postgres feature: the docs list partitioned tables, Row Level Security, check and exclusion constraints, **expression indexes**, deferred constraints and comments; it warns and comments the affected places, and the workaround is hand-added SQL in a draft migration. Relations are only picked up where a real foreign key exists (https://www.prisma.io/docs/orm/prisma-schema/introspection). Baselining is documented step by step: create `migrations/0_init`, generate its SQL with `prisma migrate diff --from-empty --to-schema ... --script`, then `prisma migrate resolve --applied 0_init` records it as applied without running it; later `migrate deploy` runs only newer migrations (https://www.prisma.io/docs/orm/prisma-migrate/workflows/baselining).
- **Trade-offs**: the most guided workflow, best known, with the strongest migration safety checks; but a second language to learn, a generate step, and a schema language that cannot express some Postgres features (the Logbook's `lower(name)` unique index is one).

### 2.3 Kysely (query builder) + a migrator
Versions: `kysely` 0.29.9 (2026-11-12, still 0.x), MIT. Not an ORM: no models, no relation magic.

- **Types**: you supply a `Database` TypeScript interface (table names to row shapes, with wrappers like `Generated<number>`). The docs recommend generating it from the production database for real apps (https://kysely.dev/docs/getting-started). The community tool `kysely-codegen` (0.20.0) does this: it "generates a `.d.ts` file from your database", one interface per table (https://github.com/RobinBlomberg/kysely-codegen). The database is the source of truth.
- **Migrations**: built in but hand-written. Each file exports `up` and `down` receiving a `Kysely<any>` (the docs insist on `any`, because a migration must not depend on today's app types), names start with an ISO date, run in alphanumeric order, and are tracked in a `kysely_migration` table. A database-level lock makes concurrent runs (several server instances) safe. Out-of-order additions error unless `allowUnorderedMigrations` is set (https://kysely.dev/docs/migrations). No automatic generation; the optional `kysely-ctl` CLI (0.22.0) creates and runs migration files but is "not part of the core".
- **Escape hatch**: a `sql` template tag that composes into queries. How typed raw results work was not in the pages read.
- **Existing database**: nothing to baseline: point codegen at the database, write queries, and start a new migration history from today. The cleanest fit for "database already exists" because it never claims to own the schema.
- **Trade-offs**: maximum control and SQL transparency; you write every migration by hand and every query shape; pre-1.0 version number.

### 2.4 TypeORM
Versions: 1.1.3 (2026-11-12), MIT; 1.0.0 shipped in May 2026 with breaking changes versus 0.3.x (https://github.com/typeorm/typeorm/releases). The oldest of the TypeScript ORMs; decorated classes ("entities") are the schema.

- **Migrations**: `typeorm migration:generate` compares entities with the live database and writes a timestamped migration file with `up`/`down` SQL; it exits with code 1 when nothing changed, so scripts must treat that as "no changes". The docs advise generating after every model change and say nothing on rename detection, so review the output (https://typeorm.io/docs/migrations/generating).
- **Escape hatch / type safety**: the query builder takes string expressions (`"user.id = :id"`) with an object of parameters; the page read says nothing about typed results, and offers raw rows via `getRawOne`/`getRawMany` (https://typeorm.io/docs/query-builder/select-query-builder). Expressions in strings are not checked by the compiler.
- **Existing database**: not covered by the pages read; the common route is writing entities by hand to match.
- **Trade-offs**: familiar to people from Java/.NET-style ORMs; weaker compile-time guarantees than the others on query strings, and `synchronize: true` is a trap with live data. Listed for completeness; this research found no source making it the better fit here.

### 2.5 Raw SQL with a migrator
A migration tool that only knows how to run SQL files, plus a plain driver (`pg`, or `postgres`) for queries.

- **dbmate**: a single standalone binary, language-independent. Migrations are plain SQL `[version]_[description].sql` with `-- migrate:up` and `-- migrate:down` sections (both required, even if down is empty). After each run it writes `db/schema.sql`, a full `pg_dump` of the schema, for committing so reviewers see schema diffs (https://github.com/amacneil/dbmate).
- **node-pg-migrate**: Postgres-only Node tool (v9.0.0, July 2026, MIT); migrations are JS functions on a `pgm` object (`pgm.createTable`, `pgm.sql` for raw SQL) with `up` and sometimes inferred `down`; needs Node 22.12+ and Postgres 14+ (https://github.com/salsita/node-pg-migrate).
- **Typed queries on top**: **PgTyped** reads your `.sql` files (or `sql` tagged strings) and generates TypeScript types for parameters and results (https://pgtyped.dev/). Its latest npm release was March 2025 (2.4.3), a staleness signal to weigh. (Prisma's TypedSQL and the Drizzle/Kysely `sql` tags are the same idea inside those tools.)
- **Trade-offs**: total control and no vendor lock-in; the SQL you write is the SQL that runs, and an existing database needs no adoption step (start numbering from today, keep a `schema.sql` snapshot). You get the least help: no inferred models, no relational fetching, and more hand-written plumbing (row-to-object mapping, insert helpers).

## 3. Comparison

| | Drizzle | Prisma | Kysely | TypeORM | SQL + migrator |
|---|---|---|---|---|---|
| Schema written in | TypeScript | Prisma schema language | SQL migrations (types generated from DB) | TS classes with decorators | SQL |
| Query style | SQL-shaped + relational API | Model-oriented client | SQL-shaped builder | Repositories / string query builder | SQL strings (typed via PgTyped etc.) |
| Types come from | Schema in code (no generate step) | Generated client | Generated `DB` interface | Entity classes | Generated per query |
| Migrations | Generated from diff, or custom SQL | Generated from diff, editable, shadow DB check | Hand-written TS (`up`/`down`) | Generated from diff, or hand-written | Hand-written SQL |
| Raw SQL escape hatch | `sql` template, inline or whole | `$queryRaw`, Unsafe variants, TypedSQL | `sql` tag | Query builder raw methods | It is the default |
| Adopt existing DB | `pull` + `--init` baseline | `db pull` + documented baseline | Codegen, no baseline needed | Hand-written entities | No adoption step |

## 4. How each handles a database that already has data

Three separate problems, often confused:

1. **Getting types for what exists.** Introspection: Drizzle `pull`, Prisma `db pull`, Kysely codegen. All work against Postgres. The risk is features the tool cannot represent. Prisma documents its list (expression indexes included); Drizzle's page lists none and was silent, so test it. Django-specific wrinkle: the existing database holds `django_*`/`auth_*` tables, and multi-table inheritance means `IndoorRoute` is a table keyed to `Route`; Drizzle's filters can exclude Django's own tables (`tablesFilter`).
2. **Making the tool's migrations start from today.** Baselining: both Drizzle (`pull --init`) and Prisma (`migrate diff` + `migrate resolve --applied`) mark the existing structure as applied. Kysely and plain SQL tools just begin a new history. The old Django migration table stays as it is and can be left alone or dropped at cutover.
3. **Moving data into a different schema.** If the rewrite changes the schema (client-generated IDs, `owner` and `updated_at` columns from the map), this is not a baseline problem but an explicit data migration: a SQL (or script) migration that copies and reshapes rows. Every option can do this with hand-written SQL; none of the tools generates it for you. Diff-based generators are riskiest here because of rename-vs-drop ambiguity; review every generated file before running it on real data, and take a `pg_dump` first (the map lists data migration as its own ticket).

## 5. Considerations that cut across all options

- **Run migrations deliberately.** Running them at app start (Drizzle `migrate(db)`, Kysely `migrateToLatest`) is simple on one VM; Kysely locks against concurrent runs, and Drizzle's docs say runtime migration suits monolithic apps. Running them as a separate deploy step is easier to reason about when something fails. Prisma's `migrate deploy` is designed to be that separate production step.
- **Keep migrations backward-compatible** when deploys are automatic, as the earlier CI/CD note (`docs/research/ci-cd.md`) argues.
- **Maturity and churn.** Two of the five (Drizzle, Kysely) have not reached 1.0 on npm; Prisma has a major (8) in release candidates; TypeORM just had a breaking 1.0. Pin exact versions and read release notes before upgrades with any of them.
- **What it costs to leave.** SQL migration files from Drizzle, Prisma, dbmate and TypeORM are plain SQL (TypeORM's can also be TypeScript), so they remain valid if you change tools; Kysely's are TypeScript calls; Prisma's schema language and generated client are the most tool-specific code.
